## 1. 프로젝트 배경

기존에는 방치형 RPG 밸런스 시뮬레이터를 개발하려 했으나, 기업 내부의 실제 밸런스 데이터 및 게임 설계 정보를 확보하기 어려웠다.

가상의 데이터를 기반으로 분석할 경우 기업에서 실제로 활용할 수 있는 결과인지 검증하기 어렵다고 판단하였다.

이에 공개적으로 접근 가능한 실제 게임 스토어 리뷰를 활용하는 유저 리뷰 분석 대시보드로 주제를 변경하였다.

## 2. 문제 정의

- 사용자: 게임 기획자 및 라이브 운영 담당자
- 상황: 출시된 게임의 사용자 리뷰를 확인하고 분석하는 과정
- 현상: 다양한 사용자 리뷰가 게임 스토어에 지속적으로 축적된다.
- 문제 가설: 다수의 비정형 리뷰에서 게임 요소별 사용자 반응과 주요 의견의 경향을 파악하기 어렵다.
- 원인 가설: 하나의 리뷰에도 여러 주제와 긍정·부정 의견이 혼재할 수 있다.
- 예상 영향: 리뷰 검토 및 주요 의견 파악에 업무 부담이 발생한다.

기업 내부의 실제 업무 환경은 확인되지 않았으므로 문제와 원인은 가설로 관리한다.

### 프로젝트 정의 한 문장

게임 기획자가 사용자 리뷰를 분석하는 과정에서 게임 요소별 반응과 주요 의견을 파악하기 어려운 불편을 감성 분석, 주제별 분류 및 데이터 시각화 기능으로 줄이는 웹앱.

## 4. 개발 원칙 및 범위

### 핵심 원칙

1. 실제 공개 리뷰 데이터를 사용한다.
2. 분석의 최소 단위는 리뷰가 아닌 개별 의견이다.
3. 하나의 리뷰에서 여러 의견을 추출할 수 있어야 한다.
4. 데이터와 기능을 분리한다.
5. 감성 분석 및 주제 분류는 사전에 수행한다.
6. 웹앱은 사전 분석 데이터를 집계하고 시각화한다.
7. 모든 분석 결과는 원본 리뷰까지 역추적할 수 있어야 한다.
8. 최종적인 판단은 사용자인 게임 기획자가 수행한다.

## 5. 기업 및 리뷰 데이터 조사

### 5.1 기업 조사

㈜에이블게임즈의 공식 홈페이지와 공식 공개 자료를 기반으로 다음 내용을 조사한다.

- 주요 사업
- 주요 게임
- 주요 고객
- 게임 개발 및 서비스 업무
- 이번 프로젝트와 관련된 업무

확인된 사실과 문제 가설을 분리한다. 각 자료에 자료명, 출처 URL, 발행일, 확인일, 확인된 내용, 확인 여부를 기록한다. 확인할 수 없는 정보는 "확인 필요"로 기록한다.

### 5.2 리뷰 수집 대상

- 게임: 달토끼 키우기, 메이플 키우기
- 플랫폼: Google Play Store, Apple App Store

플랫폼별로 실제 접근 가능한 공개 리뷰 일부를 수집한다. 모든 플랫폼에서 동일한 수량을 확보할 필요는 없으며, 실제로 확보한 데이터의 수량과 수집 조건을 기록한다.

### 5.3 데이터 수집 규칙

- 실제로 확인한 리뷰만 실제 데이터로 등록한다.
- 존재하지 않는 리뷰를 생성하지 않는다.
- 별점, 작성일, 출처 등을 추측하여 입력하지 않는다.
- 공개 리뷰 접근 및 이용 조건을 준수한다.
- 개인 식별에 불필요한 사용자 정보는 저장하지 않는다.
- 동일한 리뷰가 중복 등록되지 않도록 한다.
- 수집 기간 및 선정 방법을 기록한다.
- 표본 리뷰를 전체 이용자의 의견으로 일반화하지 않는다.
- 원문을 저장하거나 표시하는 것은 허용되는 범위로 제한한다.
- 요약과 원문을 명확히 구분한다.

웹 검색이나 리뷰 접근이 불가능한 경우 데이터를 생성하지 말고 필요한 자료를 요청한다.

## 6. 리뷰 분석 기준

### 6.1 분석 단위

하나의 리뷰를 여러 개의 독립적인 의견으로 분리한다.

예시 리뷰(설명용 가상 데이터): "전투는 재미있는데 강화 비용이 너무 비싸고 자동 사냥 중에 자꾸 튕겨요."

| 의견 | 카테고리 | 감성 | 키워드 |
|---|---|---|---|
| 전투가 재미있다 | 전투 | 긍정 | 전투 재미 |
| 강화 비용이 비싸다 | 경제 | 부정 | 강화 비용 부담 |
| 자동 사냥 중 튕긴다 | 기술·안정성 | 부정 | 비정상 종료 |

리뷰 1건과 추출 의견 3건을 구분하여 집계한다.

### 6.2 감성 분류

| ID | 분류 | 기준 |
|---|---|---|
| SENT-001 | 긍정 | 만족, 칭찬, 선호 등 긍정적 평가 |
| SENT-002 | 부정 | 불만, 불편, 문제 경험 등 부정적 평가 |
| SENT-003 | 기타 | 건의, 중립적 진술, 질문, 판단 불가 |

기타 의견 세부 유형: 건의 사항, 중립, 질문, 판단 불가. 건의 사항은 기타 의견에 포함하되 대시보드에서 별도로 조회할 수 있도록 한다. 불만과 건의가 함께 존재한다면 서로 독립적인 의미를 갖는 경우에만 의견을 분리한다. 동일한 의미를 중복 집계하지 않는다. 별점만으로 리뷰의 감성을 결정하지 않는다.

### 6.4 분류 원칙

- 하나의 개별 의견에는 하나의 주요 카테고리를 부여한다.
- 여러 주제가 독립적으로 존재하면 의견을 분리한다.
- 언급된 단어가 아닌 실제 평가 대상을 기준으로 분류한다.
- 유사한 표현은 공통 키워드로 정규화한다.
- 리뷰에 없는 의도, 원인, 문제점을 생성하지 않는다.
- 분류가 어려운 경우 판단 보류로 기록한다.
- 분류 결과는 팀원이 원문과 대조하여 검수한다.
- 카테고리 경계 규칙 RULE-01~10과 키워드 정규화 사전(`data/keywords.json`)을 따른다(B-06 결정, 19.14).

예시: 캐릭터 디자인이 예쁘다 → 아트·사운드/긍정, 캐릭터가 작아서 보기 어렵다 → UX/UI/부정, 강화하는 데 골드가 너무 많이 필요하다 → 경제/부정, 유료 패키지가 너무 비싸다 → 수익화/부정, 레벨이 너무 느리게 오른다 → 성장/부정, 파티 사냥 기능을 추가해 주세요 → 소셜/기타-건의.

## 10. 통계 계산 규칙

### 리뷰 기준 통계

- 전체 리뷰 수: 고유 reviewId의 개수
- 평균 별점: 유효한 별점의 합 / 유효한 별점이 있는 리뷰 수
- 별점 분포: 별점별 리뷰 수 / 유효한 별점이 있는 리뷰 수
- 별점이 없는 리뷰는 전체 리뷰 수에는 포함하되 평균 별점 계산에서는 제외한다.

### 의견 기준 통계

- 전체 의견 수: 고유 opinionId의 개수
- 긍정·부정·기타 비율: 해당 의견 수 / 전체 의견 수 × 100
- 건의 사항 수: 기타 의견 중 suggestion 유형의 개수
- 건의 사항은 기타 의견과 별도로 중복 합산하지 않는다.

### 카테고리별 통계

- 카테고리별 의견 수, 카테고리별 긍정·부정·기타 의견 수, 카테고리 내부 감성 비율, 전체 의견 대비 카테고리 비중
- 카테고리 내부 감성 비율과 전체 의견 대비 비중을 혼동하지 않는다.

### 키워드 통계

- 동일한 정규화 키워드를 가진 의견의 개수를 집계한다.
- 긍정 키워드와 부정 키워드는 구분하여 표시한다.
- 동일한 의견을 중복 집계하지 않는다.

### 공통 규칙

- 비율은 소수점 첫째 자리까지 표시한다.
- 분모가 0이면 N/A 또는 데이터 없음으로 표시한다.
- 반올림으로 인해 비율의 합에 미세한 오차가 발생할 수 있다.
- 실제 데이터와 샘플 데이터는 혼합 집계하지 않는다.
- ~~감성 필터는 의견 목록에 적용하며 별점 통계의 분모를 변경하지 않는다.~~ → B-04 결정(2026-11-26)으로 변경: 카테고리·감성·키워드 필터를 걸면 리뷰 통계도 "조건에 맞는 의견이 1건 이상 있는 리뷰"로 좁힌다. 상세 규칙은 19.12

## 17. Claude 작업 지침

1. 프로젝트 목적과 범위를 임의로 변경하지 않는다.
2. 실제 기업 데이터와 공개 리뷰를 추측하거나 생성하지 않는다.
3. 확인된 사실, 가설, 샘플 데이터를 구분한다.
4. 분석 결과의 근거를 확인할 수 있도록 한다.
5. 불필요한 기능이나 유료 API를 추가하지 않는다.
6. 구현에 필요한 결정을 임의로 확정하지 않는다.
7. 중요한 결정이 필요한 경우 한 번에 하나의 질문만 한다.
8. 요구 정의 → 요구 명세 → 기능 구현 → QA 사이의 추적성을 유지한다.
9. 실제 실행하지 않은 테스트를 PASS로 기록하지 않는다.
10. 현재 선택된 팀 프로젝트 폴더에서 작업한다.
11. 기존 밸런스 시뮬레이터 프로젝트 파일을 덮어쓰거나 삭제하지 않는다.
12. 파일 접근이 불가능하면 이를 명시한다.

- 수집일: 2026-11-26. 수집 지역·언어 설정은 KR/ko.
- 수집은 브라우저로 화면에 표시된 리뷰를 읽는 방식으로 했다. 대량 자동 수집 도구나 비공식 API는 사용하지 않았다.
- iTunes 검색 API(itunes.apple.com)는 브라우저 접근이 거부되었다. App Store 리뷰 페이지는 1회 429(요청 제한)가 발생했고, 재시도해서 수집했다.
- 저장하지 않은 정보: 작성자 닉네임과 프로필 이미지, '유용함' 수, 개발자 답변, 리뷰 원문 전문(`originalText`는 전부 `null`).
- 근거(`evidenceText`): B-01 결정에 따라 의견마다 원문의 짧은 발췌를 저장했다(19.9 참고). 111건 모두 발췌가 있고, 최대 길이는 37자다.
- 추적성: Google Play는 `sourceUrl`에 `&reviewId=<스토어 ID>`를 붙였다. 이 링크로 열면 해당 리뷰가 목록 첫 번째로 표시되는 것을 1건 직접 확인했다. App Store는 리뷰별 링크가 없어 리뷰 페이지 URL과 스토어 리뷰 ID(`externalReviewId`)로 추적한다.
- 작성일: B-03 결정에 따라 KST 날짜로 통일했다(19.11). 추측해서 넣은 값은 없다. `appVersion`은 웹 스토어에 표시되지 않아 전부 `null`이다.
- 산출 파일: `data/reviews.json`, `data/opinions.json`, `data/categories.json`. 분류 원장과 무결성 검사(중복 ID, 고아 의견, otherType 규칙, 의견 없는 리뷰)는 `tools/build-data.js`에 있다. 분류를 수정하면 이 스크립트를 다시 실행해 JSON을 재생성한다.

#### (3) 키워드 정규화 사전(C-06)

같은 의미의 키워드를 대표 키워드 하나로 통일한다. 사전은 `data/keywords.json`(대표 키워드, 카테고리, 통합된 이전 표현)로 분리한다. 생성 스크립트는 사전에 없는 키워드가 나오면 오류를 낸다(제안).

| 대표 키워드 | 통합 대상 | 이유 |
|---|---|---|
| 전반적 만족 | 무난함, 시간 보내기 좋음, 게임 품질 | 특정 요소를 지칭하지 않는 긍정 평가. 단, '재미'라는 표현이 직접 나온 경우는 '재미'로 유지 |
| 확률형 아이템 불만 | 확률형 아이템 불신, 뽑기 확률 낮음 | 같은 대상(뽑기)에 대한 부정 평가 |
| 광고 부담 | 광고 길이, 광고 과다, 광고 표시 불편 | 모두 광고 노출 방식에 대한 부정 평가 |
| 화면 요소 작음 | 캐릭터 크기 작음 | '화면이 작다'는 리뷰가 캐릭터를 가리키는지 확인할 수 없어 범위를 넓힘 |
| 캐릭터·외형 디자인 | 귀여운 디자인, 캐릭터 디자인, 코스튬 | 캐릭터 외형에 대한 평가 |

기타(other) 감성 키워드는 긍정·부정 키워드 순위에 넣지 않고 12.5 화면 목록에서만 보여준다(제안).
